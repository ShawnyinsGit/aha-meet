## 一、播报不完整（TTS cut-off）

### T1 — keepAlive 计时器被迟到 onend 跨清 [HIGH，已直读确认]

`speech-session.ts`：`keepAliveTimer` 是**整个 session 共享的单字段**（每条 utterance 都把自己的 interval 写进这同一个字段，:399）。但 `clearWatchdog()` 在 `advance()` 顶部**无条件**执行（:374），且清 keepAlive 的代码（:368-371）位于 B20 序号守卫（:380-381）**之前**。

时序：utterance N 的 `onend` 迟到（N+1 已经开始播）→ N 的 handler 仍进入 `advance` → `clearWatchdog` 清掉 `session.keepAliveTimer`（此刻它已属于 **N+1**）→ 再撞序号守卫 bail。结果 N+1 在无 keepAlive 状态下播放，Chromium 在 ~15s 静默截断它——正是该 workaround 想防的 bug。

触发条件由看门狗预算偏小系统性放大：`3_000 + text.length*120 + 6_000`（:408）按 ~120ms/字估算，但中文 TTS（rate 1.05）实际接近 ~180-200ms/字，长句的看门狗会**早于** `onend` 触发 → 提前 `advance()` → N+1 在 N 仍在播时启动 → N 的真 onend 迟到 → 清掉 N+1 的 keepAlive。两个独立 agent 收敛到此处。

**修复方向**：把 keepAlive interval id 捕获进 per-utterance 闭包（像 `watchdog` 那样），只清自己那个；把 keepAlive 的清理移到序号守卫之后；上调每字看门狗估算到 ~180ms。

### T2 — 140 字切分上限令 keepAlive 成为唯一防线 [HIGH]

`speech-format.ts:112-127` 把分句上限设为 140 字。140 中文字 ≈ 25s，远超 Chromium ~15s 上限——所以**每个长块都依赖 keepAlive 脉冲存活**，一旦 T1 触发即被截断。看门狗 30s 上限（:408）也救不了真实时长 > 30s 的块。

**修复方向**：把分句上限改为「稳妥低于 15s」（≈ 60-70 中文字），这样即使丢一次脉冲也只是变短而非截断。T1 + T2 应一并修，它们是同一失效模式（长块失去 15s 续命线）。

### T3 — 同轮短句被丢弃而非回灌 [MEDIUM]

`speech-session.ts:201-210`：同轮非 final 块，若 `meaningfulLen(raw) < 4` 则 `splitChunks=[]`，什么都不 push。注释声称「store 应已 hold 住」，但 `handleTalkerStreamEvent`（`meeting-store.ts:1399-1407`）实际上无条件推进 `pendingTail` 并 enqueue。因此回复中段的独立短句（「对。」「好。」）被静默吞掉。首块（sameTurn===false）与 final tail（minLen 0）不受影响。

**修复方向**：同轮路径阈值未达时，把该块回灌到下一段 pending 文本，而非丢弃。

### 已排除（核查为干净）
- **announce supersede 不会切断 talker**：每次 announce supersede 都门控在 `!isSpeechActive()`（meeting-store.ts:462），talker 流式期间 `activeSession` 在句间 40ms 间隙与 park 期保持非空，正确阻断了 announce。反向（talker 流盖掉进行中的 announce）可接受。
- **drain-hold / chunk 边界**：message_stop tail flush（meeting-store.ts:1416-1432）总带 `isFinal` enqueue 末段；`markTurnComplete`/`finalizeSession` 等 `session.current` 再 drain；`finalizeSession` 不调 `speechSynthesis.cancel()`，略早 finalize 不截音。

## 二、卡点静默（停了不说话、不请求决策）

### 看门狗：无（核心结论）

读遍 `orchestrator.ts` 与 `worker-scheduler.ts`：全系统唯一的计时器是 (a) worker→talker 合并防抖 `QUEUED_UPDATE_FLUSH_MS`（worker-scheduler.ts:774），(b) renderer announce 轮询（meeting-store.ts:478），(c) whisper ASR 探针。`handle.live.lastUpdateTs` 只被 `describeWorkers()` 按需读取（:135），**没有任何 setInterval 扫描它检测「跑太久无进展」**。

### B1 — 无 stall/idle 看门狗，挂起即零事件 [HIGH，根因]

worker 事件只来自 SDK 流（worker-scheduler.ts:361-463）。失败→announce 必须依赖 SDK `'ended'`（:433-449）。worker 卡在某 tool 中途（子 agent 卡死 / 等原生弹窗 / 死循环）**永不结束流**，`'ended'` 不触发，状态永远 `'running'`（`WorkerStatusKind` 没有 `'blocked'/'waiting'`，orchestrator-types.ts:13）。talker 输入迭代器在空队列上无限 await（claude-session.ts:329-349），委派后无消息产出即静默。announce 只能播实际触发的事件——真卡点时一个都不触发。

**修复方向**：调度器加周期性 sweep，扫 `live.lastUpdateTs`/`busy`，N 秒无进展即发合成卡点事件 +（可选）talker nudge。

### B2 — 自动批准下破坏性卡点不可见 [HIGH]

- 默认 scope `'off'`（App.tsx:69；meeting-store.ts:332），此时破坏性卡点走 renderer permission 路径、能 announce —— 这条 OK。
- 但开了自动批准后：scope `'all'` 静默放行无事件（claude-session.ts:136-138）；scope `'read'` 破坏性工具 → `confirmDestructive` → `dialog.showMessageBox`（claude-session.ts:143-152 → main.ts:245-263）—— **原生 OS 模态，不发 `permission-request` 事件**，窗口失焦时弹窗等于隐形，worker 阻塞在弹窗 promise 上。且即便事件到了 renderer，announce 还被 `autoApproveScope === 'off'` 门控掉（meeting-store.ts:999）。
- 开自动批准时 App 还把 SDK 切到 `bypassPermissions`（App.tsx:515-518），`canUseTool` 可能根本不被调。

**修复方向**：原生 confirm 前后无论 scope 都发一个 renderer 可见的卡点事件（或直接播）；别把 announce 纯按 `'off'` 门控。

### B3 — talker 提示词从未要求请求决策 / 等待口播 [MEDIUM]

`REQUEST_DECISION` 工具存在（meeting-tools.ts:15），`createDecision` 发 `decision-pending`（orchestrator.ts:405-416），该事件**确实**会 announce（meeting-store.ts:1005-1033）。但 `TALKER_PROMPT`（orchestrator-prompts.ts:6-23）**没有任何**指令要求「卡住时调 `request_user_decision`」或「workers 跑时口播进度」——只写了「信息不够 → 直接问用户」。于是 `decision-pending` 只在模型自发调用一个它从没被告知的工具时才触发，否则 worker 跑全程 talker 静默。

**修复方向**：提示词显式加「委派后需等待时要说明；需权限/抉择才能推进时调 `request_user_decision`」。

## 三、安全漏洞复查

### S1 — CLI stderr 原样转发 renderer 并展示，可能泄露 Key [HIGH，新引入]

`claude-session.ts:178-182,221-223` → `meeting-store.ts:1104-1132`。`stderr` 回调把**原始**输出推进 `stderrRing`，任一无法归类的 API 错误时取末 2000 字挂为 `msg.errorDetail`，发到 renderer 并以「详情: ${detail}」展示（还存进 `slot.lastError`）。全程无脱敏。

Key 是否出现在 stderr 取决于子进程，但多条合理路径会触发：
- 用户在 `~/.claude/settings.json` 的 `env` 里设了 `ANTHROPIC_LOG=debug` 或 HTTP verbose（settings-loader.ts:95-97 信任该处每个 key 并透传），请求头 `x-api-key`/`Authorization` 会打到 stderr。
- 行为不当的自定义网关（本 app 启用 base-url 覆盖的初衷）可能把入站 auth 头回显进 SDK 表面化到 stderr 的错误体。

Key 恰好注入该子进程（settings-loader.ts:103），任何头转储都进环并流向 UI —— 真实外泄路径。

**修复方向**：存/转发前脱敏。`stderr` 回调与构造 `errorDetail` 处都套：
```ts
const SECRET_RE = /(sk-ant-[A-Za-z0-9_-]+|(x-api-key|authorization)\s*[:=]\s*\S+)/gi;
const safe = data.replace(SECRET_RE, '$2 [REDACTED]');
```
同时脱敏 meeting-store.ts:1101 的 `contentDetail` 与 :181 的原始 `console.error`。

### S2 — API Key 明文落盘 [MEDIUM]

`store.ts:73,156`：`anthropicApiKey` 经 `JSON.stringify` 写入 `userData/settings.json`，未加密，同用户进程可读，Time Machine 备份可恢复。

**修复方向**：用 Electron `safeStorage.encryptString()`（macOS Keychain 后端）加密该字段读写；非密 `anthropicBaseUrl`/`anthropicModel` 保持原样。

### 已核实安全（不变量保持）
- `auth.ts:62-72` `auth:get-config` 返回 `hasApiKey: Boolean(...)` + 非密 baseUrl/model，从不返回 key 值。set-* 处理器不打印 key。
- `settings-loader.ts:77-112` 允许名单正确过滤，无任何 `console.*` 泄露，无 `{...process.env}`。
- 硬编码扫描干净（仅 Lobby.tsx:161 占位符 `sk-ant-...` 为误报）。

## 四、代码质量复查（近期 announce 改动）

### C1 — 切 tab / 重启会话时 announce 未清，旧播报串台 [MEDIUM]
4 个 announce 调用点入队时都按 `slot.id === this.activeId` 门控，但队列与 350ms 计时器仅在 `markBargeIn`（meeting-store.ts:500）清。`setActive`(717)/`restartSession`(1442)/`closeTab`(760)/`dispose`(517) 均不清。后果：tab A 的失败播报排队中、talker 在说，用户切到 tab B 或重启，旧行 later 经 supersede 在错误上下文播出。`restartSession` 最糟：旧失败行盖过新会话问候。

**修复方向**：`setActive`（翻转 active 后）、`restartSession`/`retryFailedTab`（重开前）、`dispose` 都加 `this.announceQueue = []; this.clearAnnounceTimer();`。

### C2 — dispose() 未清 announceTimer [LOW]
`dispose()`(517) 摘 IPC 监听但留着 pending `announceTimer`。下次触发自愈（speakCallback null 时 bail），但对测试隔离/副 renderer 是悬挂 setTimeout。与 C1 一并修。

### 已核实干净
- supersede 不切 talker（同 T1 排除项）。
- 无队列饿死 / 无界增长：每条非终止分支都重排；上限 `ANNOUNCE_MAX_QUEUE=6`；`scheduleAnnounceRetry` 防重复 arm。
- ttsOff 经 `cancelSpeech()` 清 keepAlive + drain 计时器。
- announce 的 supersede/enqueue/final 均 try + `console.warn`，未吞错。
